# Доставка на локальный стенд

Итоговая проверка в windowambassador/support-ticket-service: [отчёт, идентификаторы образов и ссылки на CI](final-report.md). Датированные результаты ниже относятся к указанным этапам разработки.

**Автор:** Горохов Георгий, 4П1.23

## Устройство доставки

В `.github/workflows/ci.yml` подготовлена цепочка `verify → image → publish → deploy`. PR выполняет только проверки и сборку. Доставка разрешена после успешной публикации на `main`, включая обычный ручной запуск. Отказ любого предыдущего задания блокирует последующие. Контрольный режим `verify_publication_gate` создаёт временный падающий тест и должен блокировать также `deploy`.

Задание доставки работает на runner с метками `self-hosted`, `Linux`, `X64`, `gorokhov-staging`. Публикация передаёт полный `image@sha256` через output задания; сборка на стенде запрещена. [compose.staging.yaml](../compose.staging.yaml) удаляет секцию `build` базового Compose через `!reset`. Приложение и PostgreSQL используют закреплённые образы.

[deploy.py](../scripts/staging/deploy.py) проверяет параметры, получает файловую блокировку, загружает образ и сравнивает digest, OCI revision и source. После запуска Compose он сравнивает ID образа работающего контейнера с загруженным образом и проверяет health. [verify_api.py](../scripts/staging/verify_api.py) отдельно проверяет HTTP-ответы readiness, категорий, списка заявок, отчёта за период и OpenAPI. Эти запросы не изменяют данные.

Основной код приложения сохраняет Modular + Layered. Скрипты эксплуатации находятся в отдельном каталоге `scripts/staging`; запуск доставки и проверки API разделены по назначению.

## Настройки

| Параметр | Значение по умолчанию |
|---|---|
| STAGING_ROOT | /srv/support-service |
| STAGING_PROJECT | support-staging |
| STAGING_PORT | 18080 |
| STAGING_WAIT_TIMEOUT | 180 секунд |
| EXPECTED_IMAGE_SOURCE | https://github.com/windowambassador/support-ticket-service |
| База и пользователь PostgreSQL | support_service |
| Адрес приложения внутри стенда | http://127.0.0.1:18080 |

Каталог стенда должен существовать и принадлежать пользователю runner. Подготовка ОС и службы описана в [инструкции стенда](local-staging.md). Перед запуском pipeline включить дистрибутив через `scripts/staging/start-local-staging.ps1` и убедиться, что runner online.

В GitHub Actions требуется repository secret `STAGING_DB_PASSWORD`: от 32 до 128 латинских букв, цифр, дефисов или подчёркиваний. 12.11.2026 секрет создан в отдельном репозитории. Значение отсутствует в исходниках и документации. Для GHCR используется временный `GITHUB_TOKEN` с `packages: read`; у задания публикации отдельное право `packages: write`. Авторизация доставки хранится в отдельном каталоге `RUNNER_TEMP` на время задания, после него выполняется `docker logout`.

При первой доставке пароль записывается в `/srv/support-service/.env` с правами `0600`. При повторной доставке содержимое сверяется; несовпадение останавливает работу до изменения контейнеров. Простая смена GitHub secret не меняет пароль существующего PostgreSQL. Ротация требует отдельной согласованной процедуры изменения пароля БД и файла окружения. Не выводить `.env`, полный `docker inspect` или раскрытый `docker compose config` в отчёт и логи.

## Релизы и результат

Для запуска GitHub используется идентификатор `<run_id>-<run_attempt>`. В каталоге `releases/<идентификатор>` сохраняются оба Compose-файла, `release.env` с digest и портом, а после успеха `deployment.json`. Файл `release.env` не содержит пароль. Повторное использование идентификатора запрещено.

`current.json` содержит последнюю успешно проверенную доставку. При следующем успехе прежняя запись переносится в `previous.json`. Запись включает SHA коммита, digest, ID образа, ID контейнера, адрес запуска GitHub, результат проверок API и время UTC. Копия результата выгружается как артефакт `deployment-<SHA>-<attempt>` на 14 дней.

Файловая блокировка защищает от параллельных локальных запусков. В workflow для стенда задана отдельная группа concurrency без отмены выполняющегося задания. PostgreSQL хранит данные в томе постоянного Compose-проекта. Каталог runner можно очищать независимо от каталога `/srv/support-service`.

При отказе health или API команда завершается с кодом 1 и сохраняет артефакт с `status: failure`; последняя успешная запись не обновляется. Контейнеры к этому моменту уже могут измениться. `current.json` означает последнюю успешную проверку, а не гарантию текущей доступности. Для управляемого возврата к предыдущему образу используется [инструкция отката](staging-rollback.md).

Если процесс прерван или runner выключен, артефакт может отсутствовать. В таком случае результат проверяется по логам задания и фактическому состоянию контейнеров; отсутствие артефакта не считается успешной доставкой.

## Проверка после коммита

1. Отправить ветку, открыть PR и дождаться успешных `verify` и `image`; `publish` и `deploy` должны быть skipped.
2. После слияния проверить все четыре задания на `main`.
3. Скачать `release-<SHA>` и `deployment-<SHA>-<attempt>`. Сверить SHA коммита и digest образа в обоих артефактах. Сравнить deployment.json с `/srv/support-service/current.json` и его imageId с ID образа работающего контейнера. Если Docker на runner сборки и на стенде используют разные хранилища, сравнить imageId из release.json с SHA-256 конфигурации образа на стенде.
4. Внутри стенда проверить `curl --fail http://127.0.0.1:18080/actuator/health/readiness` и открыть API. Публикация порта привязана к loopback; доступ из локальной сети не настраивается. Доступ из Windows зависит от localhost forwarding WSL.
5. Запустить `verify_publication_gate=true` на `main`, подтвердить отказ именно JUnit-теста, skipped у image/publish/deploy и отсутствие новых артефактов образа, публикации и доставки. Сверить контейнер и метаданные стенда до и после запуска.
6. Выполнить обычный ручной запуск без контрольного режима и повторить проверки успешной доставки.

Основной каталог `/srv/support-service` и пароль GitHub при этой проверке не используются. Локальный результат не заменяет запуск доставки через GitHub Actions. До его выполнения BL-26 и OPS-08 остаются незавершёнными.

## Локальная проверка 12.11.2026

Образ собран из исходников приложения коммита `1605f98221bf9f94fe6d69a7a598b3f5d295b73e` внутри WSL через Dockerfile проекта. Скрипты доставки проверены из рабочей копии следующего этапа. Этот прогон не является доставкой опубликованного GHCR-образа коммита 399fa4dc через Actions.

| Проверка | Фактический результат |
|---|---|
| Первая доставка по digest | Код 0, PostgreSQL и приложение healthy |
| Readiness и API | UP, 4 категории, список заявок и отчёт доступны, OpenAPI проверен |
| Mutable tag вместо digest | Код 1 до изменения контейнеров |
| Несовпадение SHA с OCI revision | Код 1; успешная версия и контейнер сохранены |
| Другой пароль существующей БД | Код 1 до изменения контейнеров |
| Контрольный образ с HEALTHCHECK CMD false | Код 1; контейнер unhealthy, current.json не изменился |
| Повторная доставка исправного digest | Код 0, health и API проверены повторно; предыдущая успешная запись сохранена |
| Секреты | Права .env равны 0600; тестовый пароль отсутствует в логах и JSON-артефактах |

Тестовый digest: `127.0.0.1:5000/support-service@sha256:28897e0894f45d8cc6d0ca15527f1a3bc7ffb75374291eb44e256830beab4c73`. В Docker Engine 29.9.3 с containerd image store этот образ имеет тот же строковый ID; совпадение проверено через inspect образа и контейнера. Это конкретный результат данного Engine, а не правило равенства digest registry и ID во всех окружениях.

Материалы в рабочей копии: `build/bl26-image-build.log`, `bl26-deployment-check.log`, `bl26-deployment-verification.json`, `bl26-deployment-evidence.tar`, `bl26-test-cleanup.log`. Архив содержит журналы и JSON шести сценариев; секреты и файл .env в него не входят. Каталог build игнорируется Git и удаляется clean, поэтому перед очисткой материалы для защиты нужно сохранить отдельно.

После проверки временные контейнеры приложения, PostgreSQL и registry удалены; том тестовой БД и локальные результаты оставлены. Основной Compose-проект support-staging ещё не развёрнут. Docker Engine и runner продолжают работать для будущей доставки через pipeline.

# Речь к защите

Горохов Георгий, 4П1.23

## 1. Сервис обработки заявок

Меня зовут Георгий Горохов. В рамках практики я разработал сервис технической поддержки. Для сотрудника службы поддержки основной объект здесь заявка. У неё есть категория, приоритет и история обработки. Руководителю нужна другая информация: сколько обращений поступило за период, сколько решено и какие открытые обращения уже просрочены. Эти две задачи определили устройство приложения. В докладе я прослежу путь одной заявки от регистрации до завершения, покажу, где соблюдаются правила перехода статуса, и разберу, как собранный образ попадает на стенд.

## 2. Что сохраняется при обработке заявки

В примере сотрудник сообщает о принтере, который перестал отвечать. При создании обязательны заголовок и существующая категория. Начальный статус устанавливает сервер. Исполнитель берёт обращение в работу, а после решения закрывает его. Возможен и другой исход: обращение можно отменить. У каждого перехода есть время. Когда пользователь читает историю, он должен увидеть тот же путь, что и в карточке. Поэтому я сохраняю новый статус и запись истории в одной транзакции. Если одна часть операции завершается ошибкой, в базе не должно остаться наполовину применённого перехода.

## 3. Терминальный статус защищён правилом

Здесь прослеживается одно требование от постановки до теста. Закрытую заявку нельзя вернуть в работу этим API. Контроллер принимает HTTP-запрос и передаёт его сервису. Сервис получает актуальное состояние заявки под блокировкой и проверяет допустимость перехода. В сквозном сценарии rejectsTerminalChangesWithoutChangingAnyView я создаю заявку, провожу её через два перехода и фиксирую состояние перед запрещённым запросом. После ответа 409 повторно читаю данные. Так проверяются две вещи: клиент получает понятную ошибку, а в истории не появляется событие, которого не происходило. Тест повторяется отдельно для завершения и отмены.

## 4. Как Java и Kotlin считают один отчёт

Основное приложение работает в одном процессе Spring Boot. Модули ticket, category и report разделены по предметной области, а внутри находятся контроллеры, сервисы и репозитории. В отчёте Java-реализация ReportDataSource читает из PostgreSQL заявки, созданные в выбранном интервале. Левая граница входит, правая исключена: соседние периоды не пересекаются. Kotlin-сервис группирует выборку по статусам и приоритетам и вычисляет среднее время решения. Выбор nullable-показателя здесь имеет смысл для пользователя: если ни одна заявка ещё не решена, среднего не существует. Второе решение касается точности: длительности суммируются с дробной частью, округление происходит после деления. Через интерфейс источника в модульном тесте я могу подставить заранее известные записи.

## 5. Три уровня проверки

В тест-плане я связываю сценарий с требованием и ожидаемым результатом. Один параметризованный метод может выполниться несколько раз, поэтому количество сценариев и выполнений JUnit различается. Модульные тесты проверяют логику при управляемом времени. Для просрочки это особенно важно: момент точно на границе срока и момент сразу после него дают разные результаты. Интеграционные тесты запускают настоящий PostgreSQL и проверяют, что миграции, ограничения таблиц и запросы работают совместно. Сквозной сценарий воспроизводит действия клиента по HTTP. Если заменить базу заглушкой, останутся непроверенными особенности хранения времени и поведение транзакций, поэтому эти уровни дополняют друг друга. В артефакте CI первого pull request я проверил 507 выполнений без ошибок и пропусков. Счётчик строк JaCoCo показывает 488 покрытых строк из 499. Одиннадцать оставшихся строк полезнее анализировать по конкретным путям выполнения. Сам процент не объясняет, например, проверено ли сохранение истории после отказа; для этого и нужен отдельный сквозной сценарий.

## 6. Два дефекта и их регрессии

Первый дефект удалось воспроизвести короткой строкой из пяти единиц через дефис. Преобразователь мог построить UUID, хотя внешний контракт требует полную запись. В результате клиент получал ответ не по той причине, по которой следовало отклонить запрос. Теперь исходная строка сначала проходит проверку групп длины восемь, четыре, четыре, четыре и двенадцать. Регрессионный тест проверяет и другие неверные формы. Второй дефект проявлялся на границе отчёта при работе со старыми календарными датами. Ошибка находилась в передаче Instant через JDBC. После выбора типа с часовым поясом я повторил граничные тесты на PostgreSQL. В журнале приведены условия воспроизведения и результаты до и после исправлений.

## 7. Что проверяет доставка

GitHub выполняет форматирование, сборку и тесты, а результаты JUnit и JaCoCo сохраняет в артефактах. Следующее задание собирает Docker-образ. При слиянии в main тот же образ переносится через артефакт и публикуется в GHCR с тегом полного SHA. Для доставки я использую digest, поскольку он однозначно указывает содержимое образа. На стенде скрипт сверяет источник и ревизию, запускает PostgreSQL и приложение и ждёт health check. Затем он отдельно запрашивает readiness, категории, заявки, отчёт и спецификацию OpenAPI. Только после этих действий в current.json появляются идентификатор контейнера и метаданные проверенного релиза. Секрет БД передаётся заданию через GitHub Actions.

## 8. Диагностика и восстановление

Если сервис перестал отвечать, сначала смотрю состояние контейнеров. При недоступной базе важно отличить остановленный процесс PostgreSQL от ошибки параметров подключения. Для этого проверяю pg_isready внутри контейнера и журнал приложения. Если база уже принимает подключения, смотрю readiness Spring Boot и причину в логе. Третий случай возникает раньше: миграция Flyway может остановить запуск приложения. Тогда я нахожу номер миграции и исходное сообщение PostgreSQL. Удаление рабочего тома уничтожило бы данные, поэтому для экспериментов использовал отдельную базу. Проверку резервной копии я тоже выполнял отдельно: восстановил архив, сравнил данные и проверил вставку следующей записи. На практике резервная копия нужна при проблемах с данными, а возврат версии приложения использует существующий совместимый том.

## 9. Заявка «Проверка принтера» на стенде

Это фактический результат обращения к развёрнутому сервису. Контрольная заявка начинается с идентификатора 0563375f. Я выбрал существующую категорию «Оборудование», указал высокий приоритет и получил ответ 201. Первый запрос PATCH перевёл заявку в работу. Второй завершил её, и сервер записал время закрытия. Третий запрос попытался перевести ту же заявку обратно в работу. Он получил 409 с кодом STATE_CONFLICT. Я повторно запросил карточку и историю и сравнил ответы с состоянием до отказа. Записей по-прежнему две. Вызов отчёта вернул одну решённую заявку высокого приоритета и среднее время 0,070044 секунды. Переходы выполнялись скриптом вслед друг за другом. Это длительность именно учебной заявки, а не оценка скорости работы службы поддержки.

## 10. Первая доставка на gorokhov-staging

В запуске первой доставки видны все четыре задания. Первые три выполняются на инфраструктуре GitHub. Четвёртое выполняет мой self-hosted runner gorokhov-staging. Внутри Ubuntu у него есть доступ к Docker. Пакет загружается по полному digest, который я сверил с артефактом публикации. В release.json и deployment.json совпадают ревизия и digest. На этом стенде Docker выводит ID по манифесту, а на сборочном runner ID соответствует конфигурации. Поэтому я дополнительно сверил SHA-256 конфигурации экспортированного образа. После запуска два контейнера стали healthy. Запрос readiness на порту 18080 с Windows также вернул UP. Полные идентификаторы сохранены в отчёте. Эта ссылка ведёт именно на выполненную доставку.

## 11. Падающий тест остановил доставку

После первой успешной доставки я намеренно запустил контрольный режим на main. Это существенно: на pull request доставка пропускается по условию ветки даже при исправном коде. Здесь же без ошибки она должна была выполниться. В свежей рабочей копии runner временно создаётся PublicationGateProbeTest с явным падением. В скачанном JUnit XML присутствует отказ именно этого теста. Зависимые задания image, publish и deploy получили skipped. До запуска и после него я прочитал current.json, карточку, историю заявки и readiness. Значения совпали, включая ID контейнера. Такой контроль позволяет показать, что ранее работавший сервис продолжает обслуживать запросы, даже когда очередной запуск проверки завершился ошибкой.

## 12. Как прошёл возврат с B на A

Я доставил вторую версию через тот же pipeline. Для проверки отказа health check запустил этот образ в отдельном проекте Compose и заменил его проверку здоровья командой, которая возвращает ошибку. В журнале видно состояние unhealthy. Временные контейнеры удалились, а основной сервис продолжил работу. Затем я выполнил команду отката уже на основном стенде. Она прочитала previous.json и пересоздала приложение из сохранённого образа A. Изменился контейнер приложения, а PostgreSQL продолжил работать на прежнем томе. Я сверил digest, получил UP от readiness, повторно прочитал заявку и сравнил оба события истории. Так я проверил и версию приложения, и пользовательские данные. Этот способ возврата требует совместимой схемы базы.

## 13. Что можно проверить после сдачи

За 72 академических часа я прошёл путь от требований до работающего сервиса. Для повторения проверки я бы начал с README и коллекции запросов: создал заявку, провёл её до решения, запросил историю, затем посмотрел отчёт по периоду. Для проверки доставки в итоговом отчёте есть ссылки на запуски и полные идентификаторы образов. Их можно сопоставить с данными контейнера на стенде. У решения есть ограничения. Сейчас API используется в учебной среде без разграничения доступа. Повторный запрос на создание после обрыва связи может создать вторую заявку. При переносе сервиса за пределы стенда я в первую очередь добавил бы аутентификацию и защиту от повторной отправки. Спасибо за внимание.
